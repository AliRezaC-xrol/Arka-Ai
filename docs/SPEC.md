# Arka — Build Spec (نسخه‌ی نهایی)

> این فایل جایگزین کامل پروژه‌ی قبلی است. پروژه از صفر، روی GitHub، با نام **Arka** ساخته می‌شود.

---

## 0. نحوه‌ی استفاده با z.ai (GLM Agent Mode)

1. یک ریپوی خالی و **private** روی GitHub بساز، اسمش `arka`.
2. یک **Personal Access Token** با دسترسی `repo` بساز (GitHub → Settings → Developer settings → Fine-grained tokens) و در z.ai به ایجنت بده تا بتونه push/commit بزنه.
3. این فایل رو محلی نگه دار (یا در اولین پیام به‌عنوان فایل به ایجنت بده) به اسم `docs/SPEC.md`.
4. برای هر فاز، پرامپت اون فاز رو به‌ترتیب توی z.ai (Agent Mode، مدل GLM) بفرست. صبر کن هر فاز کامل تموم بشه، تست کن، بعد فاز بعد.
5. هیچ فازی رو رد نکن؛ فازهای بعدی روی فرض تمام‌شدن فاز قبلی سوار می‌شن.

## 2. معماری و مدل داده (Prisma schema خلاصه)

```prisma
model User {
  id            String   @id @default(cuid())
  email         String   @unique
  name          String?
  image         String?
  authProvider  String   // "google" | "email"
  createdAt     DateTime @default(now())
  lastSeenAt    DateTime?
  isBanned      Boolean  @default(false)
  bannedAt      DateTime?
  bannedReason  String?
  timeoutUntil  DateTime?
  timeoutReason String?
  conversations Conversation[]
  providerKeys  UserProviderKey[]
  usageEvents   UsageEvent[]
  notifications Notification[]
  sessions      Session[]
}

model EmailOtp {
  id        String   @id @default(cuid())
  email     String
  codeHash  String
  expiresAt DateTime
  attempts  Int      @default(0)
  consumedAt DateTime?
  createdAt DateTime @default(now())
}

model AdminSession {
  id        String   @id @default(cuid())
  tokenHash String   @unique
  createdAt DateTime @default(now())
  expiresAt DateTime
}

model Provider {
  id          String   @id @default(cuid())
  scope       String   // "global" (ادمین اضافه کرده، همه می‌بینن) | "user" (فقط خود کاربر)
  ownerUserId String?  // فقط برای scope=user
  name        String   // اسمی که ادمین/کاربر می‌ذاره و روی سایت نشون داده می‌شه
  kind        String   // openai | anthropic | google | openai_compatible | ...
  baseUrl     String?
  enabled     Boolean  @default(true)
  createdAt   DateTime @default(now())
  keys        ProviderKey[]
  models      ProviderModel[]
}

model ProviderKey {
  id            String   @id @default(cuid())
  providerId    String
  label         String
  ciphertext    Bytes
  iv            Bytes
  tag           Bytes
  status        String   @default("unknown") // ok | invalid | exhausted
  lastCheckedAt DateTime?
  priority      Int      @default(0)  // ترتیب استفاده برای failover
  createdAt     DateTime @default(now())
}

model ProviderModel {
  id           String  @id @default(cuid())
  providerId   String
  modelId      String
  displayName  String
  supportsChat Boolean @default(true)
  supportsImage Boolean @default(false)
  enabled      Boolean @default(true)
}

model UserProviderKey {
  // پروایدرهای شخصی کاربر (scope=user در Provider بالا مدیریت می‌شه، این فقط رفرنس سریع است)
  id         String @id @default(cuid())
  userId     String
  providerId String
}

model Conversation {
  id        String   @id @default(cuid())
  userId    String
  title     String
  createdAt DateTime @default(now())
  updatedAt DateTime @default(now())
  messages  Message[]
}

model Message {
  id             String   @id @default(cuid())
  conversationId String
  role           String   // user | assistant | system
  contentJson    String   // متن، تصویر، بلوک کد
  providerId     String?
  modelId        String?
  tokensIn       Int?
  tokensOut      Int?
  createdAt      DateTime @default(now())
}

model UsageEvent {
  id           String   @id @default(cuid())
  userId       String
  providerId   String
  modelId      String
  tokensIn     Int
  tokensOut    Int
  createdAt    DateTime @default(now())
}

model Notification {
  id          String   @id @default(cuid())
  userId      String?  // null یعنی برای همه (broadcast)
  broadcastId String?  // گروه‌بندی پیام‌های همگانی برای حذف دسته‌جمعی
  title       String
  body        String
  readAt      DateTime?
  dismissedAt DateTime?
  createdAt   DateTime @default(now())
}

## 3. احراز هویت (بخش حیاتی)

### 3.۱ ورود با گوگل
OAuth استاندارد Google از طریق Auth.js. اولین بار که کاربر با یک ایمیل وارد می‌شود، رکورد `User` ساخته می‌شود. **دفعات بعد با همان ایمیل** (چه از طریق گوگل، چه از طریق ایمیل/کد) باید به **همان رکورد** وصل شود، نه رکورد جدید. کلید یکتا برای این تطبیق، `email` است.

### 3.۲ ورود با ایمیل + کد
1. کاربر ایمیلش را وارد می‌کند.
2. کد ۶ رقمی تصادفی تولید و **هش‌شده** در `EmailOtp` ذخیره می‌شود (پلین‌تکست کد هرگز در DB نیست)، انقضا ۱۰ دقیقه، حداکثر ۵ تلاش اشتباه.
3. ایمیل با قالب HTML سفارشی (طبق بخش ۷) ارسال می‌شود.
4. کاربر کد را وارد می‌کند؛ در صورت درست بودن، اگر ایمیل قبلاً وجود داشت همان `User` استفاده می‌شود، وگرنه ساخته می‌شود؛ سشن ایجاد می‌شود.
5. Rate limit: حداکثر ۳ درخواست کد در ۱۰ دقیقه برای هر ایمیل/IP.

### 3.۳ سشن
JWT یا دیتابیس-بک (`Session` جدول Auth.js)، کوکی `HttpOnly; Secure; SameSite=Lax`. `lastSeenAt` روی هر درخواست معتبر آپدیت می‌شود (برای شمارش «آنلاین‌های الان» در ادمین: کسانی که `lastSeenAt` در ۵ دقیقه‌ی اخیر است).

### 3.۴ بن و تایم‌اوت (اثر روی ورود)
- در `middleware`/`callback` سشن: اگر `isBanned = true` → خروج فوری از سشن + صفحه‌ی «حساب شما مسدود شده».
- اگر `timeoutUntil` در آینده باشد → کاربر می‌تواند وارد پنل شود ولی چت/تولید غیرفعال است و یک بنر نشان می‌دهد: «به دلیل [reason] تا [mm:ss] نمی‌توانید از هوش مصنوعی استفاده کنید» با شمارش معکوس زنده. بعد از پایان زمان، خودکار فعال می‌شود.

## 4. مدیریت Provider و کلید (هسته‌ی فنی مهم)

### 4.۱ دو نوع Provider
- **Global (ادمین اضافه می‌کند):** برای همه‌ی کاربران در انتخاب مدل قابل مشاهده و استفاده است. نام دقیقاً همانی که ادمین وارد کرده، در پنل کاربر نمایش داده می‌شود.
- **User (خود کاربر اضافه می‌کند):** فقط در لیست مدل‌های همان کاربر ظاهر می‌شود و بقیه نمی‌بینند.

### 4.۲ افزودن Provider (فرم کامل، بدون باگ)
فیلدها: نام نمایشی، نوع (OpenAI / Anthropic / Google / سازگار با OpenAI با Base URL دلخواه / سازگار با Anthropic)، Base URL (اختیاری برای انواع سازگار)، یک یا چند کلید API با برچسب و اولویت.

**اعتبارسنجی اتصال (باید همیشه دقیق باشد):**
1. بلافاصله بعد از افزودن، درخواست تستی واقعی به Provider زده می‌شود (لیست مدل‌ها یا یک پینگ سبک).
2. نتیجه به‌صورت واضح در UI: `متصل ✓` (سبز فقط همین‌جا، چون وضعیت است نه رنگ برند)، `نامعتبر ✕`، یا `در دسترس نیست`.
3. اگر خطا داد، پیام خطای واقعی Provider (خلاصه‌شده) نمایش داده شود، نه پیام مبهم.
4. دکمه‌ی «تست دوباره» همیشه در دسترس است.

### 4.۳ چند کلید برای یک Provider + Failover خودکار
- هر Provider می‌تواند چند `ProviderKey` با `priority` داشته باشد.
- موتور فراخوانی مدل، کلیدها را به ترتیب `priority` امتحان می‌کند.
- اگر یک کلید خطای `quota_exhausted` یا `auth_invalid` بدهد → همان لحظه، **بدون دخالت کاربر و بدون قطع پاسخ**، به کلید بعدی با `priority` پایین‌تر سوییچ می‌شود و `status` کلید خراب به‌روزرسانی می‌شود.
- اگر همه‌ی کلیدهای یک Provider تمام شدند → پیام روشن به کاربر: «همه‌ی کلیدهای [نام Provider] تمام شده‌اند» (نه خطای فنی خام).
- این رفتار متفاوت از پروژه‌ی قبلی (فاز‌به‌فاز پرسیدن از کاربر) است: چون اینجا کلیدها متعلق به سرویس/ادمین یا خود کاربرند و هدف تجربه‌ی بی‌وقفه است، سوییچ **خودکار** انجام می‌شود؛ فقط وقتی چیزی برای سوییچ نمانده پیام داده می‌شود.

### 4.۴ نمایش در انتخاب‌گر مدل
لیست مدل‌ها به تفکیک Provider نمایش داده می‌شود؛ اسم دقیقاً همانی که هنگام افزودن Provider وارد شده. کاربر می‌تواند بین Providerهای Global و Providerهای شخصی خودش سوییچ کند.

## 5. محیط اصلی چت

- ساختار مثل ChatGPT/Claude: سایدبار با تاریخچه‌ی گفتگو (فقط مال خود کاربر، ایزوله در سطح دیتابیس با `userId`)، دکمه‌ی گفتگوی جدید، ستون اصلی وسط‌چین.
- **قابلیت‌ها:** چت متنی با استریم، تولید تصویر (اگر مدل انتخاب‌شده از نوع image باشد رابط جدا: پرامپت + گرید نتایج)، نمایش بلوک کد با syntax highlight و دکمه‌ی کپی، markdown کامل، انتخاب مدل از بالای پنجره‌ی چت.
- **افکت انتخاب (خواسته‌ی کلیدی UI):** یک باکس کم‌رنگ (پس‌زمینه‌ی نرم + بردر بسیار کم‌کنتراست) دور آیتم فعال سایدبار/تب قرار دارد. با کلیک روی آیتم دیگر، این باکس **animate** می‌شود و با حرکت نرم (نه پرش) به موقعیت جدید می‌رود؛ پیاده‌سازی با اندازه‌گیری `offsetTop/offsetLeft/width/height` آیتم مقصد و انیمیشن `transform` با easing نرم (`cubic-bezier(0.65,0,0.35,1)`، حدود ۳۰۰-۴۰۰ میلی‌ثانیه). باید در RTL هم درست کار کند.
- گفتگوها Auto-save می‌شوند؛ تغییر نام گفتگو، حذف، جستجو در تاریخچه.

## 6. هیرو و لندینگ

- طراحی حرفه‌ای، **بدون شلوغی**: یک هدر خط اول قوی (نام Arka + یک جمله)، زیرش توضیح کوتاه، دکمه‌ی «شروع کنید».
- معرفی قابلیت‌ها: نه به‌صورت پاراگراف طولانی، بلکه بلوک‌های کوتاه (آیکون + عنوان کوتاه + یک جمله)، هرکدام هنگام اسکرول با انیمیشن ورود ملایم (fade + کمی جابه‌جایی، نه پرشی) ظاهر می‌شوند (scroll-triggered reveal، با `IntersectionObserver`).
- بخش‌های پیشنهادی هیرو: هدر اصلی، معرفی چت هوشمند، معرفی تولید تصویر، معرفی «هر Provider که بخواهی وصل کن»، معرفی امنیت و ایزوله بودن حساب‌ها، CTA پایانی.
- انیمیشن‌ها ظریف و کوتاه؛ `prefers-reduced-motion` رعایت شود.

## 7. صفحه‌ی ورود و ایمیل OTP

### 7.۱ صفحه‌ی ورود
طراحی خاص و متفاوت از فرم‌های معمولی: پس‌زمینه‌ی مینیمال مشکی با یک جلوه‌ی ظریف (مثلاً گرادیانت نوری بسیار کم‌کنتراست یا الگوی نقطه‌ای که به آرامی حرکت می‌کند)، کارت ورود با گوشه‌ی نرم، دو دکمه: «ورود با گوگل» و «ورود با ایمیل». انتخاب ایمیل → فیلد ایمیل → صفحه‌ی وارد کردن کد با ۶ باکس جدا (auto-focus بین باکس‌ها، paste-friendly).

### 7.۲ قالب ایمیل کد ورود
HTML تمیز و برند‌شده (مشکی/سفید مطابق پالت Arka)، لوگوی متنی Arka بالا، کد به‌صورت بزرگ و فاصله‌دار در یک باکس، متن «اگر شما درخواست نداده‌اید نادیده بگیرید»، انقضا ذکر شود (۱۰ دقیقه). سازگار با کلاینت‌های ایمیل (inline CSS، بدون فریم‌ورک‌های خارجی).

## 8. داشبورد ادمین (`/c-xroladi1n`)

### 8.۱ ورود ادمین
مسیر مخفی، فرم فقط رمز عبور (جدا از سیستم کاربران، در env یا جدول `AdminCredential` با هش argon2id). محدودیت تلاش ناموفق. سشن جدای `AdminSession`.

### 8.۲ صفحه‌ی نمای کلی (Overview)
- کارت‌های آماری: تعداد کل کاربران ثبت‌نامی، تعداد کل پیام‌های رد و بدل شده، کاربر با بیشترین مصرف (نام/ایمیل + عدد)، تعداد کاربران آنلاین همین الان (`lastSeenAt` در ۵ دقیقه‌ی اخیر، با به‌روزرسانی زنده).
- نمودار روند ثبت‌نام (خط یا میله‌ای، بازه‌ی روزانه/هفتگی/ماهانه قابل انتخاب) + عدد کل ثبت‌نامی‌ها کنارش.
- Uptime سایت: زمانی که سرویس از آخرین ری‌استارت بالا بوده + درصد uptime بازه‌ی اخیر (با یک health-check ساده‌ی داخلی که پینگ‌های دوره‌ای را ثبت می‌کند).

### 8.۳ صفحه‌ی Providers (ادمین)
- افزودن/ویرایش/غیرفعال‌سازی Provider سراسری با همان فرم بخش ۴.
- برای هر Provider: لیست کلیدها با وضعیت، اولویت (قابل drag/تنظیم عدد)، آمار مصرف کلی آن Provider (توکن ورودی/خروجی، تعداد درخواست).
- نمودار مقایسه‌ی مصرف بین Providerها (کدام Provider بیشترین مصرف را داشته).
- برای هر Provider: لیست «پرمصرف‌ترین کاربران آن Provider خاص» (نام/ایمیل + مقدار).
- صفحه‌ی «مصرف کلی»: جمع کل توکن مصرف‌شده در کل سیستم + تفکیک بر اساس هر Provider جداگانه با نمودار.

### 8.۴ صفحه‌ی مدیریت کاربران
- جدول همه‌ی کاربران: نام، ایمیل، تاریخ و ساعت دقیق ثبت‌نام، تعداد پیام، آخرین بازدید، وضعیت (عادی/بن/تایم‌اوت).
- جستجو (نام/ایمیل) و فیلتر/دسته‌بندی (بر اساس وضعیت، تاریخ عضویت، میزان مصرف).
- کلیک روی هر کاربر → صفحه‌ی جزئیات: اطلاعات کامل، گفتگوهای اخیر (فقط متادیتا، نه لزوماً محتوای خصوصی کامل — این را به‌عنوان یک تصمیم حریم خصوصی به تو واگذار می‌کنم، پیش‌فرض: فقط آمار، نه متن کامل چت‌ها)، Providerهای شخصی که اضافه کرده، مصرف او به تفکیک Provider.
- عملیات: **Ban** (کلیک، دلیل اختیاری، اثر فوری و تا زمانی که ادمین Unban نکند)، **Timeout** (انتخاب مدت زمان از یک لیست یا مقدار دلخواه دقیقه/ساعت + دلیل اختیاری، اثر فوری، قابل حذف دستی زودتر از موعد توسط ادمین).
- صفحه‌ی «کاربران بن‌شده» و صفحه‌ی «کاربران تایم‌اوت‌شده» با دکمه‌ی رفع در همان لیست.

### 8.۵ پیام‌رسانی ادمین
- فرم ارسال: انتخاب «به یک کاربر خاص» (جستجو با ایمیل) یا «به همه»، عنوان و متن.
- پیام به‌صورت Notification در پنل کاربر ظاهر می‌شود (زنگوله/بنر).
- حذف: پیام تکی قابل حذف برای همان کاربر؛ پیام همگانی با یک دکمه برای همه‌ی گیرندگان حذف می‌شود (با `broadcastId` مشترک).

## 9. امنیت

- کلیدهای Provider با AES-256-GCM رمزنگاری، هرگز کامل به فرانت برنمی‌گردند.
- کدهای OTP هش‌شده، نه پلین‌تکست.
- Rate limit روی: درخواست OTP، ورود ادمین، افزودن Provider.
- بررسی مالکیت: کاربر فقط به گفتگوها و Providerهای خودش دسترسی دارد (بررسی `userId` در هر query).
- ورودی‌های کاربر قبل از درج در پرامپت به‌عنوان داده نه دستور در نظر گرفته می‌شود (جلوگیری از prompt injection ساده).
- HTTPS در پروڈاکشن الزامی (ریدایرکت خودکار).

:root {
  --bg: #000000; --bg-elevated: #0d0d0d; --bg-card: #121212;
  --text: #ffffff; --text-2: #a0a0a0; --text-3: #6b6b6b;
  --border: rgba(255,255,255,.10); --hover: rgba(255,255,255,.06);
  --radius-control: 10px; --radius-card: 16px;
  --accent-blue: #2f7bff; /* تنها رنگ تأکیدی: اکشن اصلی، حالت فعال، focus ring، glow کم */
  --font-sans: -apple-system, BlinkMacSystemFont, "Vazirmatn", system-ui, sans-serif;
}
```
فقط همین یک تم. بدون سایه، فقط hairline border. انیمیشن‌ها کوتاه (۰.۲ تا ۰.۴ ثانیه). کامپوننت‌های vibefarsi (button, calendar, price) و کامپوننت‌های Skiper/Microkit که در پروژه‌ی قبلی ممیزی و ساخته شدند (از جمله باکس اسپاتلایت برای انتخاب آیتم‌ها) اینجا هم استفاده می‌شوند؛ هرچه از Skiper در دسترس نبود، طبق تجربه‌ی فاز قبلی، نسخه‌ی اورجینال ساخته می‌شود، هرگز کپی از نسخه‌ی پولی نمی‌شود.

## 11. فازبندی

| فاز | خروجی | معیار قبولی |
|---|---|---|
| **۰** | ریپوی GitHub، اسکلت Next.js، دیتابیس، تم و فونت، هیرو (استاتیک با موشن اسکرول)، صفحه‌ی ورود (فقط UI، بدون بک‌اند واقعی) | هیرو و لاگین با داده‌ی ساختگی، ریسپانسیو، انیمیشن اسکرول کار می‌کند |
| **۱** | احراز هویت واقعی: گوگل + ایمیل OTP، جدول User، جلوگیری از حساب تکراری، سشن | ورود دوباره با همان ایمیل حساب جدید نمی‌سازد؛ ایمیل OTP واقعی می‌رسد |
| **۲** | محیط چت اصلی + افزودن Provider (ادمین و کاربر) + انتخاب مدل + استریم پاسخ | یک پیام واقعی با یک Provider واقعی جواب می‌گیرد؛ باکس انتخاب سایدبار نرم حرکت می‌کند |
| **۳** | چند کلید در هر Provider + failover خودکار + تولید تصویر + تاریخچه‌ی گفتگو کامل | با غیرفعال‌کردن دستی یک کلید، سیستم خودکار به کلید بعدی سوییچ می‌کند بدون قطع پاسخ |
| **۴** | داشبورد ادمین: Overview + نمودار ثبت‌نام + Uptime | اعداد Overview با داده‌ی واقعی دیتابیس مطابقت دارد |
| **۵** | ادمین: صفحه‌ی Providers با آمار مصرف و نمودار مقایسه‌ای | مصرف واقعی هر Provider و پرمصرف‌ترین کاربرش درست نمایش داده می‌شود |
| **۶** | ادمین: مدیریت کاربران کامل (جستجو، جزئیات، بن، تایم‌اوت) | بن/تایم‌اوت فوراً روی حساب کاربر واقعی اثر می‌کند؛ شمارش معکوس تایم‌اوت درست است |
| **۷** | ادمین: پیام‌رسانی (تکی/همگانی) + حذف پیام | کاربر پیام را به‌عنوان نوتیف می‌بیند؛ حذف همگانی برای همه کار می‌کند |
| **۸** | صیقل نهایی: امنیت، سرعت، رفع باگ اتصال Provider، دیپلوی | بدون خطای اتصال Provider، بدون نشت کلید در لاگ/فرانت |

## 12. تعریف «تمام‌شده»

- [ ] ورود با گوگل و ایمیل هر دو کار می‌کند و حساب تکراری نمی‌سازد.
- [ ] هر کاربر فقط گفتگوها و Providerهای خودش را می‌بیند.
- [ ] افزودن Provider همیشه دقیق تست و نمایش داده می‌شود (متصل/نامعتبر).
- [ ] چند کلید در یک Provider با failover خودکار و بدون وقفه کار می‌کند.
- [ ] داشبورد ادمین تمام آمار خواسته‌شده (کاربران، پیام‌ها، مصرف، نمودار ثبت‌نام، آنلاین‌ها، Uptime) را نشان می‌دهد.
- [ ] بن، تایم‌اوت (با شمارش معکوس به کاربر)، و رفع آن‌ها کار می‌کند.
- [ ] پیام‌رسانی تکی و همگانی + حذف آن‌ها کار می‌کند.
- [ ] UI فقط سیاه/سفید، فونت وزیر برای فارسی و استک اپل برای انگلیسی، افکت اسپاتلایت نرم بین آیتم‌های انتخابی.
